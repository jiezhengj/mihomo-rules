# Mihomo 项目宪章

## 核心原则

### 一、公开与私有配置边界

对外发布的模板和文档不得包含个人订阅、节点信息、私人网络地址或其他可识别的个人配置。个人配置必须与公开文件隔离，并保持在 Git 跟踪范围之外。公开模板之间的共同路由与协议架构应保持一致；确需本地差异时，将其限制在个人配置中并说明用途。

### 二、分层路由与容灾

业务规则必须使用具备适当 fallback 能力的路由组，不得直接依赖单个原子测速或节点选择组。路由组及其 fallback 结构应便于在节点或线路故障时恢复连接。业务策略组的具体职责、选择条件和业务覆盖范围由当前获准的 Feature 需求定义，不由本宪章固定到某组服务、产品或流量类别。

### 三、基于证据的平台与资源适配

配置必须针对项目实际支持的运行环境及其已知能力、资源预算和兼容性要求设计。增加、保留或移除规则数据与功能时，必须依据当前用途、资源实际内容和适用平台证据，并记录重要取舍。

选择路由资源时，必须先以已确认的流量意图为准，优先评估能够覆盖目标意图且边界适用的较完整资源。不能仅因某项服务知名、资源名称熟悉或资源粒度较细，就默认优先引入针对该服务或细分场景的资源；Apple、Google 等细分资源也遵循这一原则。应从适用上游项目提供的各种资源形态中选择最合适者，不把“规则集”预设为唯一资源类型。

只有具体场景证据表明，按原则性资源与顺序处理仍会造成以下误分流之一，且调整顺序无法解决或会引入新的路由问题时，才可考虑采用更细资源：不应代理的流量被送入代理；非大流量代理操作被送入 `ROUTE_GLOBAL`；大流量代理操作被送入 `ROUTE_AI`。细分必须针对已证明的覆盖差异，并审阅其对其他场景和首匹配结果的影响。不得仅凭服务名称、协议标签、流量规模或历史动作推断资源适用范围。过时或不再适用的能力不因历史配置曾经包含而自动保留；本宪章不维护易随产品和上游变化的服务、规则集或资源名称清单。

### 四、按当前业务意图设计路由

路由判断必须依次确认：是否应拦截；对不应拦截的流量，是否需要代理；对需要代理的流量，是否属于大流量。应拦截的流量走 `REJECT`；不应拦截但不需要代理的流量必须走 `DIRECT`；需要代理的大流量优先考虑 `ROUTE_GLOBAL`，需要代理的非大流量默认进入 `ROUTE_AI`。没有匹配已确认规则的流量由 `PROXY` 兜底。服务名称本身不能代替对具体操作意图和规模的判断；具体业务类别和路由组职责由当前 Feature 定义。

规则动作和顺序必须来自具体 Feature 中已确认的业务意图、资源覆盖证据及首匹配影响。原则性资源与顺序必须先能满足上述路由意图；只有在第三原则所列的具体误分流无法仅通过调整顺序安全解决时，才可考虑更细的匹配资源。

### 五、可用性与可恢复性

配置模式应满足其声明的使用方式。需要单机场景的配置应能以单个有效订阅启动；提供多来源选择的配置应保留清楚、可操作的故障切换路径。任何具体模板的启动条件和切换行为由对应 Feature 定义并验证。

## 项目范围与技术边界

本项目维护 Mihomo 配置及其相关说明。项目级原则用于约束配置边界、容灾结构、证据质量和平台适配；具体平台清单、规则资源、服务类别、策略组业务范围、路由顺序及单项功能取舍由当前获准的 Feature 文档定义。Feature 可以在不违反本宪章长期原则的前提下调整这些细节。

不同平台或配置模式可以存在有理由的差异。共享业务路由和协议架构应保持一致；平台专属裁剪及本地个人用途差异应有明确边界和依据。

## 工作流与质量门禁

配置变更必须针对所有受影响的模板和个人配置核对共同策略是否一致，并按变更范围记录配置解析、首匹配行为、数据引用及文件边界的验证结果。未运行的检查不得报告为通过；没有设备或运行时证据时，不得把资源预算要求描述成实测达标。

采用或调整上游规则数据时，必须审阅其来源、用途、覆盖边界及与其他规则的交叠。规则顺序应能解释已确认场景的预期首匹配结果。公开内容须检查个人信息和私有配置字段；个人配置须保持未跟踪。

## 治理

本宪章规定项目长期适用的原则，不代替 Feature 对具体业务行为和实现选择的定义。Feature 需求、计划或配置与本宪章冲突时，必须先通过正式修订解决冲突；不得靠忽略原则或将临时实现细节默认为永久政策来绕过。

修订本宪章时，必须记录影响范围并更新版本：移除或重新定义现有原则时递增 MAJOR；新增原则或显著扩展治理要求时递增 MINOR；不改变约束含义的澄清和编辑递增 PATCH。每次设计与审查只核对受变更影响的原则，并记录实际适用的质量门禁。
