本指南定义 Feature 实施完成后维护者如何检查交付。它是执行时的验证步骤，本规划阶段没有运行配置测试。

# 前置条件

- 在仓库根目录执行命令。
- 准备实现阶段记录的 Mihomo 稳定版本及可执行文件；在本机确认命令 `mihomo` 可用。计划核对到的稳定发布为 `v1.19.32`，执行时应记录实际版本并复核是否变化。
- 个人订阅字段仅在本机的 local-only 配置中填写；不要复制到公开模板、规范或公开验证记录。
- 确认 `` 下应有 8 份公开模板和 4 份本地配置，并确认历史基线归档没有覆盖源文件。

# 1. 检查文件矩阵与私有边界

1. 枚举 Desktop、Docker、iOS、Android 各自的 single/dual 公开模板，共 8 份。
2. 枚举每平台 1 份个人配置，共 4 份；检查它们及个人历史归档都匹配 `.gitignore` 规则，且不被 Git 跟踪。
3. 对比公开模板中的订阅字段，确认只含 `YOUR_SUBSCRIPTION_LINK_HERE` 等公开占位值；扫描真实订阅、节点标识、私有策略组、内网信息和个人规则字段，命中项逐个审阅。
4. 将归档公开文件与归档前原文件比较；个人文件只在本地做哈希/内容比对，不复制进受跟踪归档。

预期结果：矩阵数量、平台/模式组合正确；个人文件仍被忽略；公开内容无私有字段；公开历史归档与原始公开文件一致。

# 2. 运行 Mihomo 配置解析

对每个模板及本机存在的个人配置，使用同一个已记录版本的 Mihomo 核心做配置检查：

```powershell
mihomo -t -f mihomo_config_desktop_single_template.yaml
```

把路径替换为矩阵内其余配置路径。若目标客户端要求特定工作目录或 profile 参数，依该客户端的受支持方式补充；不可把一份配置的通过结果外推至其他文件。

预期结果：每个实际检查的配置均由目标 Mihomo 版本接受；记录核心版本、文件路径和原始退出状态。未执行或失败的配置必须列明。

# 3. 审阅规则声明、场景首匹配和矩阵同构

针对 [数据模型](data-model.md) 的规则集合、路由规则和配置矩阵逐项审阅：

- 每项被引用资源有对应声明，固定来源、revision、资源路径、匹配行为和格式可追溯；代表成员审阅注明范围及抽样边界。资源选择遵循“原则性”：优先覆盖最完整且边界适用的资源，不因服务知名或名称熟悉而默认引入 Apple、Google 等细分资源。若考虑更细资源，须记录具体操作及意图、相关资源成员/匹配语义、当前首匹配规则与动作、预期动作，并用受影响场景说明为什么调整顺序不能消除误分流或会造成另一误分流。仅当证据指向三类规定误分流之一时才触发评估；抽样不得宣称为全量证明。
- 代表场景记录具体操作、拦截意图、代理意图、仅对需代理操作适用的规模类别和 `scale_basis`（预期传输特征、该操作归类理由、依据来源）、预期动作，以及配置中第一个实际匹配的规则。服务名、CDN 身份或集合名不足以单独决定规模；不设数值阈值或运行时字节切换，证据不足标待确认。
- 按“应拦截 → `REJECT`；否则不应代理 → `DIRECT`；否则需要代理的非大流量 → `ROUTE_NORMAL`；需要代理的大流量 → `ROUTE_HEAVY`；未匹配 → 最后 `PROXY`”的顺序核对意图。验收覆盖非大流量代理、大流量代理、维护者点名的屏蔽样例、未匹配兜底及 Desktop 游戏内容下载的通用 DIRECT 意图与集合边界；不按服务品牌另设验收项或优先级。`ROUTE_NORMAL` 的基础候选顺序为 `AUTO_STRICT`、`AUTO_GENERAL`，`ROUTE_HEAVY` 为 `AUTO_GENERAL`、`AUTO_STRICT`；仅当某份配置定义 `AUTO_BACKUP` 时才核对它是否为第三候选。逐份配置核对并仅引用其实际定义的候选组。候选链按配置类型区分：4 份个人配置为三级链（`ROUTE_NORMAL: AUTO_STRICT → AUTO_GENERAL → AUTO_BACKUP`、`ROUTE_HEAVY: AUTO_GENERAL → AUTO_STRICT → AUTO_BACKUP`）；8 份公开模板不拆节点池，`ROUTE_NORMAL` 与 `ROUTE_HEAVY` 均 fallback 到单一 `AUTO` 组。组名不定义业务类别。
- 检查已识别的集合交集、域名后缀可能重叠及 CIDR 包含关系；记录首匹配结果和仍未确认的成员。
- 业务规则不直接引用 `AUTO_XXX`；策略 fallback 符合 `ROUTE_NORMAL → AUTO_STRICT`、`ROUTE_HEAVY → AUTO_GENERAL` 的首选关系。
- 通用路由在 8 份公开模板中同构；平台专属裁剪有说明。
- iOS 正则兼容、移动平台裁剪、Docker TUN/监听/Sniffer 边界和 Desktop 必要能力均符合宪章。

预期结果：所有已确认场景首匹配动作一致率 100%；不确定成员标记待确认而不计为通过；`PROXY` 在每个模板中最后；没有悬空声明。

# 4. 记录 iOS 内存证据边界

检查交付说明是否标明 iOS Network Extension 的 15 MB 上限仍须设备实测。如果实施范围没有另行批准并定义目标客户端、环境、峰值或常驻指标及可复现方法，应保持 `待实测`，不得将 YAML 检查或规则数量当作内存符合证明。
