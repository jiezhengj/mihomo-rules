# 决策 1：按操作意图与传输规模路由

**Decision**：分流判断依次为：先判断是否应拦截，应拦截的走 `REJECT`；未拦截的再判断是否需要代理，不应代理的走 `DIRECT`；需要代理时，非大流量操作走 `ROUTE_NORMAL` 并首选 `AUTO_STRICT`，大流量操作走 `ROUTE_HEAVY` 并首选 `AUTO_GENERAL`。两个 ROUTE 都是 fallback 策略组，基础候选顺序为 `ROUTE_NORMAL: AUTO_STRICT → AUTO_GENERAL`、`ROUTE_HEAVY: AUTO_GENERAL → AUTO_STRICT`；仅当某份配置实际定义 `AUTO_BACKUP` 时，才可将其作为第三候选。本 Feature 的 8 份公开模板不拆节点池，`ROUTE_NORMAL` 与 `ROUTE_HEAVY` 均 fallback 到单一 `AUTO` 组；4 份个人配置使用三级链并以 `AUTO_BACKUP` 作末位逃生。所有配置均不得引用自身未定义的候选组。组名中的 AI 不定义流量业务类别。流量规模描述具体操作的预期传输特征，不要求运行时按字节动态切换，同一服务可因操作不同而有不同规模特征。将操作归为大流量时，须在场景表记录特征（如批量载荷、长时媒体传输，或实际承载图片/视频载荷的 CDN 操作）、分类理由及依据来源；服务名、CDN 身份或集合名本身不足以定类。本 Feature 不设数值阈值；可审阅依据不足时标为待确认，不计作已验证场景。

**Rationale**：流量规模决定需要代理的操作首选哪条容灾路径，不决定拦截意图或代理意图。Desktop 游戏内容、补丁或分发切片下载按通用操作边界审阅；商店、社区、推荐和营销操作按各自已确认意图处理，不按服务品牌区分。

**Alternatives considered**：按 `ROUTE_NORMAL` 名称推断 AI 业务、按服务名固定分类、按实时吞吐量自动切换、按旧配置 provider 名称继承分类。这些做法分别误解了策略组名、混淆不同操作的业务意图、超出静态规则能力，或违反不迁移旧 provider 分类的约束。

# 决策 2：先确认场景与覆盖证据，再决定规则数据和首匹配次序

**Decision**：资源选择遵循“原则性”：先依据已确认的流量意图审阅并优先采用覆盖最完整且边界适用的资源；不因服务知名或名称熟悉而默认选择 Apple、Google 等细分资源。必须从 MetaCubeX `meta-rules-dat` 的所有适用资源形态中选择最合适者，而不预设只使用规则集。逐项记录资源、固定版本来源和路径、匹配对象/行为和格式、代表性成员及审阅范围、混合用途/覆盖限制、与其他入选数据的交集，以及受首匹配影响的已确认场景。若考虑更细资源，触发记录还须列明具体操作及拦截/代理意图、相关成员或匹配语义、当前首匹配规则和动作、预期动作，以及评估的顺序调整及其不能消除原误分流或会造成另一误分流的场景证据。只有证据表明原则性资源与顺序导致以下误分流之一，且调整顺序无法解决或会引入新的路由问题时，才考虑更细资源：不应代理的流量进入代理；非大流量代理操作进入 `ROUTE_HEAVY`；大流量代理操作进入 `ROUTE_NORMAL`。域名后缀匹配和 IP CIDR 包含关系须按相应匹配语义审阅；只比较文件名或类别名不构成覆盖证明。代表成员审阅须说明是抽样还是全量及其边界，抽样不得声称全量证明。无法支持单一目标动作且明显含反向用途的集合不得整体绑定该动作，应记录缺口及规则组级选项。

路由意图按固定判断顺序处理：先识别应拦截流量并指向 `REJECT`；对其余流量判断是否需要代理，不需要代理的一律指向 `DIRECT`；需要代理时，非大流量操作指向 `ROUTE_NORMAL`，大流量操作指向 `ROUTE_HEAVY`。`ROUTE_NORMAL` 基础顺序为 `AUTO_STRICT → AUTO_GENERAL`，`ROUTE_HEAVY` 基础顺序为 `AUTO_GENERAL → AUTO_STRICT`；仅当配置本身定义 `AUTO_BACKUP` 时，才可将其作为第三候选。8 份公开模板不拆节点池，`ROUTE_NORMAL` 与 `ROUTE_HEAVY` 均 fallback 到单一 `AUTO` 组；4 份个人配置使用三级链并以 `AUTO_BACKUP` 作末位逃生。任何模板或个人配置都不得引用自身未定义的候选组。组名不用于推断业务类型。未命中时最后由 `PROXY` 兜底。集合交叠按该意图顺序和具体成员证据审阅，并记录首匹配结果。更细资源只能用于上述三类原则性误分流，并须先证明调整顺序无法安全解决；不得因 Apple、Google 等名称或知名度本身而采用细分资源。维护者须点名至少一个 `REJECT` 代表场景并记录屏蔽依据。任何业务规则都不得直接指向 `AUTO_XXX`。

**Rationale**：固定快照审阅已观察到域名数据间存在精确交集和可能因后缀语义扩大的重叠；目录名和数据发布者均不足以推出成员的个人路由意图。项目宪章要求业务策略经过 `ROUTE_XXX` 容灾组，并禁止为覆盖缺口添加单服务例外。

**Alternatives considered**：按类别名称选择整组；逐项将旧 provider 映射到新动作；为每个未覆盖服务创建规则；让规则集合名称决定拦截或代理意图。这些做法不能由具体操作及成员证据支持，或违反项目规则。决策顺序由已确认的业务操作意图定义，不由服务品牌提高优先级。

# 决策 3：将规则段作为一个整体设计，旧配置只按授权边界作参考

**Decision**：`rule-providers` 前的配置内容可参考旧配置重建；自 `rule-providers` 声明开始，provider 与后续 `rules` 均作为一个整体，依据新场景、数据审阅和先匹配决策重新设计。旧 12 份配置保留基线副本。明确指定的 Tailscale、UU 远程、绿联 NAS 只在相应个人配置按平台处理，先审查平台适用性与重叠；不得进入公开模板。建议新矩阵目录 ``，其中 `README.md` 概述矩阵和来源；场景与集合审阅、检查结果保存于本地文档（均不随仓库发布）；建议历史基线目录 `archive/meta-rules-unification-baseline/`。

**Rationale**：这满足 Spec 中完整矩阵、独立目录、公开/个人隔离及旧配置归档要求，并限制旧配置的用途，避免历史规则牵引新规则设计。

**Alternatives considered**：覆盖根目录旧模板；仅生成规则草案、不交付矩阵；把所有历史个人文件纳入 Git 归档。这些都不满足完整交付、保留历史或私有数据边界。

# 决策 4：发布 8 个公开模板和 4 个本地个人配置的同构矩阵

**Decision**：公开矩阵为 Desktop、Docker、iOS、Android × single/dual，共 8 个 `*_template.yaml`；个人矩阵为四个平台各 1 个无 `_template` 后缀的本地配置。通用策略组与路由意图保持同构，平台裁剪依宪章执行：移动端剔除其规定的重型资源，Desktop 保持适用的游戏/大文件能力，Docker 关闭 TUN、限制监听面并启用 Sniffer，iOS 使用兼容的负向先行断言节点过滤。个人配置值只存在本地忽略文件中。

**Rationale**：项目宪章已完整规定平台与机场模式矩阵、容灾组和设备边界，无需新增技术栈或服务。

**Alternatives considered**：所有平台完全相同的数据列表；以统一配置覆盖单机场/双机场差异；将个人字段写入公开模板。这些选择违反明确的平台或隐私约束。

# 决策 5：以核心解析、场景首匹配审阅和边界检查构成交付验证

**Decision**：实现阶段对 8 个公开模板和可用的本地个人配置运行同一已记录版本 Mihomo 核心的配置检查，并针对代表场景逐条核对首匹配动作；另检查规则引用存在、矩阵同构、公开文件无私有字段、个人文件被 Git 忽略，以及平台裁剪。场景记录验证拦截意图、未拦截流量的代理意图、需代理操作的规模分类及最终兜底；Desktop 游戏本体、补丁或分发切片下载按通用操作边界核对 `DIRECT` 意图和规则组覆盖，不按服务品牌另设验收项。iOS Network Extension 的 15 MB 运行时内存上限仍是硬约束，但 Assessment B 不包含测量；没有设备、客户端、指标口径和可复现测量结果时，只报告待实测，不能宣称符合。

**Rationale**：Mihomo 语法解析不能单独证明规则覆盖或用户意图；静态成员和顺序审阅也不能替代实际设备内存测量。分层证据可分别说明这些边界。

**Alternatives considered**：只做 YAML 语法检查；用旧 provider 数量推断资源占用；将历史 15 MB 声明视为新规则运行时已合格。都不能支撑 Spec 的成功标准。
